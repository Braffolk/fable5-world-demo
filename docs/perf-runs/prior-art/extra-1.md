# Prior-art brief: StarsX/ComputeRaster — bin → tile → pixel software rasterizer in compute (HLSL/D3D12)

- **Source kind**: repo (full source, no paper). A working real-time compute-shader software rasterizer by Tianchen Xu (XUSG author).
- **Repo**: `docs/perf-runs/prior-art/sources/ComputeRaster/` (shallow clone, last commit `ef60bdf` 2025-03-11). Hot device code: `ComputeRaster/Content/Shaders/{BinRaster,TileRaster,PixelRaster}.hlsl`, helpers `Common.hlsli`, `VSStage.hlsl`, `SharedConst.h`. CPU orchestration: `ComputeRaster/Content/SoftGraphicsPipeline.cpp`.
- **Fetched**: `git clone --depth 1` (OK, ~small). All four raster shaders + common headers + the C++ driver read in full. No PDF/paper exists; the README is the only prose. Doc/ has only result JPEGs.

## Why this source matters (and how it differs from the CudaRaster brief)
ComputeRaster is a **concrete, compact, readable implementation of exactly the Laine-Karras sort-middle pipeline** that `laine2011-cudaraster.md` describes in theory. It is the same three-stage bin→coarse(tile)→fine(pixel) architecture, but in HLSL compute that ports almost mechanically to WGSL (no CUDA warp intrinsics in the core path; the wave-ops are optional `#if SHADER_MODEL>=6` fast-paths with a portable `InterlockedAdd` fallback). Two things make it independently valuable beyond the CudaRaster brief:

1. **It implements the "small triangle bypasses binning" decision in a single readable function** (`GetTileInfo`, `TileRaster.hlsl:204-225`) — the precise lever the mission flagged ("triangles smaller than 4×4 tiles bypass binning and go direct to pixel rasterization, matching our ~1px regime").
2. **Its depth election is exactly the no-64-bit-atomic family we live in**: a 32-bit `RWTexture2D<uint>` depth target updated with `InterlockedMin` over `asuint(z)`, plus a separate color write — NOT a 64-bit depth|payload InterlockedMax. So unlike CudaRaster (which sidesteps atomics entirely via per-warp-owned tiles), ComputeRaster shows a **directly comparable** 32-bit-atomic visibility scheme and exposes both a fast non-watertight variant and a slow watertight mutex variant. This is the most apples-to-apples election comparison in the source set.

**Honest caveat up front**: ComputeRaster is a *demo*, not a tuned production rasterizer. It is built for triangle counts in the 10k–100k range (Stanford bunny/dragon/venus), not our 36M visible tris. Several of its choices (per-tile `globallycoherent` HiZ with `InterlockedMin`, the `[allow_uav_condition]` time-out guards, the mutex color path) would be *slower* than our current scheme at our scale. The value here is the **architecture and a few specific micro-decisions**, not a drop-in port. I flag the traps explicitly.

## Raster architecture (4 compute dispatches, sort-middle)
Sizes (`SharedConst.h`): TILE = 8×8 px (`TILE_SIZE_LOG=3`), BIN = 64×64 px (`TILE_TO_BIN_LOG=3`, so a bin = 8×8 tiles). Pipeline (`SoftGraphicsPipeline.cpp:449-630`):

1. **Vertex stage** (`VSStage.hlsl`): `numthreads(64,1,1)`, 1 thread : 1 vertex. Runs the user VS, writes clip-space `g_rwVertexPos[vid]` + attributes to typed buffers. Dispatched as `DIV_UP(numVertices,64)`. Note: it processes *vertices*, not triangles — no per-triangle vertex re-fetch at this stage (relevant to our 40% transform cost; see T4).

2. **Bin raster** (`BinRaster.hlsl`, named file but contains the *bin* logic in `TileRaster.hlsl`… see note): actually the **binning pass is `TileRaster.hlsl`'s `main` is the tile pass**; the *binning* compute is the file `BinRaster.hlsl` whose `main` (`TileRaster.hlsl:402-420`) does 1 thread : 1 triangle: cull → to-screen → `ProcessPrimitive`. `ProcessPrimitive` (`TileRaster.hlsl:230-281`) decides via `GetTileInfo` whether the triangle is "big" (area > (8×8)×(4×4) px) — if so it bins into 64×64 bins; **otherwise it writes tile-primitive records DIRECTLY into the tile queue and skips the coarse pass entirely**. Dispatched `DIV_UP(numTriangles,64)`.

3. **Tile (coarse) raster** (`TileRaster.hlsl:24-99`): `numthreads(8,8,1)`, **one workgroup per binned primitive** (`SV_GroupID` indexes `g_roBinPrimitives`), 64 threads = the 8×8 tiles inside one bin. Each thread tests its tile against the (conservatively dilated) triangle via `Overlap`, does an optional per-tile HiZ `InterlockedMin`, and appends surviving (tile,prim) records to the tile queue. **Dispatched indirectly** (`ExecuteIndirect` off `m_binPrimCount`) so only as many workgroups as there are binned prims.

4. **Pixel (fine) raster** (`PixelRaster.hlsl:58-147`): `numthreads(8,8,1)`, **one workgroup per tile-primitive**, 64 threads = the 64 pixels of an 8×8 tile. Each thread: load 3 verts, to-screen, `Overlap` test for its pixel, barycentric-normalize, interpolate z, `InterlockedMin` depth, **early-out if it lost the depth race**, then interpolate attributes + run the pixel shader + write color under a depth-guarded mutex. **Dispatched indirectly** off `m_tilePrimCount`.

Key structural facts for our purposes:
- **Work distribution is "one workgroup per (binned-prim / tile-prim)", dispatched indirectly from GPU-written counts** (`SoftGraphicsPipeline.cpp:601,628` `ExecuteIndirect`). This is *between* our "one workgroup per cluster" and a persistent-thread model. The triangle→tile fan-out is materialized into a queue and consumed by an indirect dispatch, so the GPU sizes its own launch.
- **The fine pass is tiled but does NOT use shared-memory depth.** Depth lives in a *global* `RWTexture2D<uint> g_rwDepth` and is contended with `InterlockedMin` across all workgroups touching a pixel (`PixelRaster.hlsl:105`). This is the same global-atomic-per-fragment shape as ours — so ComputeRaster is NOT an example of the shared-memory-depth win (that is CudaRaster's T5). Its tiling only reduces *coverage candidate set*, not depth contention.

## Depth/visibility ELECTION and the no-64-bit-atomic mapping (critical)
ComputeRaster has **three** depth structures, all 32-bit `uint` textures, all atomic-min over `asuint(z)` (smaller z = nearer = wins, the natural inverse of our inverted-key-max but identical in spirit):

- **BinZ** (`RWTexture2D<uint>`, per 64×64 bin) and **TileZ** (per 8×8 tile): coarse HiZ, updated with `InterlockedMin(zMax)` and tested `if (hiZ < zMin) cull` (`TileRaster.hlsl:68-76`, `BinRaster/TileRaster bin loop:174-194`). Conservative occlusion: a primitive is dropped only if its nearest z is behind the farthest z already recorded in that tile. **This is the conservative tile-granularity HiZ — same family the mission already refuted at cluster granularity, and ComputeRaster confirms the mechanism but NOT a win for holey foliage.** Note it is marked `globallycoherent` and uses `DeviceMemoryBarrier()` for the non-atomic reads — expensive; see trap below.

- **PixelZ** (`g_rwDepth`, per pixel): the real depth buffer. Two code paths (`PixelRaster.hlsl:94-147`):
  - **`USE_MUTEX 0`** (fast, non-watertight): `InterlockedMin(g_rwDepth[px], depth, old)`; if `depth > old` return (lost). Then run PS, then `DeviceMemoryBarrier(); if (depth == g_rwDepth[px]) writeColor`. **This is structurally identical to our scheme**: one atomic on a 32-bit depth word elects a winner, the winner writes its payload (here color directly; for us the id side-store) guarded by an equality re-check. The comment even admits "not fully watertight, but is faster and works in most cases" (`PixelRaster.hlsl:140`) — i.e. a same-depth tie can let two fragments both write, last-writer-wins.
  - **`USE_MUTEX 1`** (watertight, slow): a spin-lock per pixel via `InterlockedExchange(depth, 0xffffffff, old)` to grab the lock, critical-section compare-and-write color+depth, loop until acquired (`PixelRaster.hlsl:122-138`). This is a true per-pixel mutex — correct but catastrophically slow under our 12-20× overdraw; do NOT port.

**Mapping to our packed (24b depth | 8b tiebreak) atomicMax + id side-store:** ComputeRaster's `USE_MUTEX 0` path is the same idea but splits depth (atomic) from payload (separate guarded write). The lesson is *not* a new election trick — we already do the equivalent and ours is arguably better (single atomicMax carries the tiebreak; the winner plain-stores the full id). What ComputeRaster adds is **negative evidence**: it shows the two obvious alternatives — (a) per-pixel mutex spin-lock, and (b) `globallycoherent` HiZ textures with `DeviceMemoryBarrier` — and both are clearly worse than our relaxed-atomicLoad-then-conditional-max for dense overdraw. This corroborates the mission's "SW atomic contention is not the bottleneck" finding: the contention reducer (mutex) is the slow path, not the fast one.

## Conservative rasterization & coverage math (the genuinely transferable micro-tech)
This is where ComputeRaster is most concretely useful, because its coverage primitive is small and cleanly factored:

- **Edge-function setup is done ONCE per triangle** in screen space: `n` = the 3 edge normals, plus `w` = unnormalized barycentrics evaluated at the AABB min-corner (`TileRaster.hlsl:250-263`, `Common.hlsli:111-131`). Then per-tile/per-pixel coverage is an **incremental dot-product**: `w += mul(n, pos - minPt); return all(w >= 0)` (`ComputeUnnormalizedBarycentric` / `Overlap`, `Common.hlsli:90-106`). That is exactly our "3 integer edge tests + barycentric-z" per fragment — but note the setup (edge normals, min-corner bary) is hoisted out of the per-fragment loop. **Confirms our hot-loop shape is canonical**; the lever is hoisting setup, which we largely do.

- **Conservative edge dilation via `Scale`** (`Common.hlsli:61-85`): to make a tile "overlap" test conservative (cover any tile the triangle touches, not just tiles whose center is inside), each vertex is pushed outward by half a tile along the two incident edges using a cross-product plane intersection. `Scale(v, 0.5)` dilates (for coverage), `Scale(v, -0.5)` *shrinks* (used for the HiZ "is this tile fully inside?" test, `TileRaster.hlsl:64-68`). This dilate/shrink pair is the standard way to get conservative coarse coverage without 64-bit masks. **Relevant if we ever go tiled** (T1): coarse tile coverage for tiny tris needs this or it will miss tiles.

- **Small-triangle bypass** (`GetTileInfo`, `TileRaster.hlsl:204-225`): `area = determinant(v0,v1,v2)` in pixels; if `area > (TILE·TILE)·(4·4)` (= a 32×32 px footprint) use bins, else write straight to the 8×8 tile queue. For our ~1px leaf cards, **every triangle takes the bypass** — it would never enter the bin/coarse pass at all, going straight from setup to a tile queue keyed by a single tile. This is the mission's named lever, and ComputeRaster shows it is a *one-comparison* decision.

## Scanline binning (avoids per-tile point tests across the AABB)
`BinPrimitive` (`TileRaster.hlsl:137-199`) does NOT test every tile in the AABB. For each tile-row it scans left→right to find the first overlapping tile (`scanLine.x`) and continues until it exits (`scanLine.y`), then **emits the contiguous run `[x,y)` in one shot** via `AppendPrimitive` (`TileRaster.hlsl:98-132`), incrementing `TileIdx` along the run. This is a span/scanline fill at tile granularity — it skips the outside-triangle bbox tiles, the tile-level analogue of the per-pixel scanline x-span we already shipped (commit `19eb834`). Confirms our scanline approach is the right shape; offers the *row-run emit* (one atomic reservation for a whole contiguous run of tiles) as a refinement.

## Transferable techniques

### DIRECT ports (mechanism transfers to WGSL with modest effort)

**T1 — One-comparison small-triangle bypass of the binning stage (`GetTileInfo`, `TileRaster.hlsl:204-225`).**
If a triangle's screen area ≤ a tile-block threshold, skip bin/coarse and emit directly into a fine-tile queue keyed by its single overlapping tile. For our ~1px tris this means the *entire* triangle population skips two pipeline stages. **Adapt**: this only matters if we adopt a tiled fine pass at all (T5 in the CudaRaster brief). On its own it is a no-op for us because we are *already* effectively "all small" — the insight is that a tiled redesign for us does NOT need the bin/coarse stages at all; we can bin tiny tris straight into one fine-tile bucket each. That collapses the "every tri must traverse bin+coarse" fixed cost the CudaRaster brief warned about (its §6.2 caveat). Pure integer area compare, no atomics, fully WGSL-portable. **Quality-preserving** (exact area test).

**T2 — Hoisted edge-equation setup + incremental barycentric (`Common.hlsli:90-131`, `TileRaster.hlsl:250-263`).**
Compute the 3 edge normals `n` and the min-corner unnormalized barycentric `w` ONCE per triangle; per fragment do only `w += mul(n, pos-minPt); all(w>=0)`. **Adapt**: we already do this in the cluster/tri setup — verify our hot loop carries `n` and `w0` and does NOT re-derive edge normals per fragment. If any per-fragment edge re-derivation remains, this removes it. WGSL-portable, no atomics. **Quality-preserving.**

**T3 — Conservative dilate/shrink edge offset for coarse coverage (`Scale`, `Common.hlsli:61-85`).**
If/when we bin tiny tris into tiles (T1/T5), the tile-overlap test must be *conservative* or sub-tile tris fall through tile-center tests. `Scale(v,+0.5)` dilates verts outward by half a tile for the coverage test; `Scale(v,-0.5)` shrinks for the "fully-covered" HiZ test. **Adapt**: needed only under a tiled redesign; it is the correct way to avoid 64-bit coverage masks for the coarse step. WGSL-portable (pure float cross-products), no atomics. Note: dilation is conservative → never drops a covered pixel, so **quality-preserving** (it can over-include tiles, costing a little work, never under-include).

**T4 — Vertex stage processes vertices once, not per-triangle (`VSStage.hlsl:37-49`).**
ComputeRaster transforms each *vertex* exactly once (`numthreads(64)`, 1 thread:1 vertex) into a `g_rwVertexPos` buffer; the raster passes then *index* into it (`g_rwVertexPos[primId*3+i]`). Note the raster passes still re-fetch 3 verts per triangle from that buffer, but the **expensive VS work (and, for us, the 48 wind texture taps) runs once per vertex, not once per triangle-instance**. **Adapt — directly attacks our 40% transform+launch**: the mission says we do `3× fetchWorldVert` with ~5× redundant re-fetch and ~48 wind taps *per triangle inside the hot kernel*. ComputeRaster's structure says: run wind animation + world transform in a **separate vertex-bake pass** writing post-animation positions to a buffer, then have the raster kernel read pre-transformed positions (cheap buffer loads) instead of re-running 48 taps per triangle. The redundant re-fetch collapses from per-triangle to per-vertex (the ~5× shared-vertex amortization). This is a real structural lever for our 40%, and it is exactly how every conventional pipeline avoids re-shading shared verts. WGSL-portable; the bake pass needs a vertex-dedup index (we have clusters → cluster-local vertex buffers already). **Quality-preserving** (identical math, just memoized).

**T5 — GPU-sized indirect dispatch off a compacted work queue (`SoftGraphicsPipeline.cpp:386-393, 601, 628`; `BinRaster.hlsl:81-98` wave-coalesced append).**
The triangle→tile fan-out is written into a queue with a GPU-incremented count, then consumed by `ExecuteIndirect` whose threadgroup count = the count. The append uses **wave-coalesced atomics** (`WaveActiveCountBits`/`WavePrefixCountBits` → one `InterlockedAdd` per wave, `BinRaster.hlsl:82-94`) to cut atomic traffic on the queue counter. **Adapt — attacks the 40% launch model**: instead of statically launching `QRASTER_CAP×128` (one workgroup per cluster, many idle), build a compact list of *populated tiles* (or visible clusters) on the GPU and `dispatchWorkgroupsIndirect` off its count. WGSL supports `dispatchWorkgroupsIndirect` and 32-bit `atomicAdd`; the wave-coalesced append maps to WGSL subgroup ops (`subgroupAdd`/`subgroupExclusiveAdd`, available on Metal via the subgroups feature) with a plain `atomicAdd` fallback. This is the "let the GPU size its own launch + coalesce the queue atomic" pattern. Note the mission's prior "submit/BFS-pass batching was marginal" finding is about a *different* axis (CPU submit batching), not GPU-side indirect compaction. **Quality-preserving.**

### INDIRECT ports (adapt the principle; bigger refactors)

**T6 — Row-run (scanline) emit: one atomic reservation per contiguous tile run (`BinPrimitive`/`AppendPrimitive`, `TileRaster.hlsl:137-199, 98-132`).**
Rather than one queue-append per covered tile, the binner finds the contiguous overlapping span `[x,y)` per row and reserves `len = y-x` slots with a **single** `InterlockedAdd`, then fills the run. **Adapt (principle)**: anywhere we have variable per-producer fan-out into a queue (clusters→tiles, or tris→fragments), reserve the whole run/count with one atomic and fill locally, instead of per-element atomics. Combine with subgroup-coalescing (T5). Reduces atomic traffic on append counters under skew. WGSL-portable. **Quality-preserving.**

**T7 — Decouple coverage candidate-set reduction from depth (what ComputeRaster does NOT do, stated as a lever).**
ComputeRaster's tiling reduces the *coverage candidate set* (a fine workgroup only sees tris binned to its tile) but still resolves depth in a **global** atomic texture (`PixelRaster.hlsl:105`). The CudaRaster brief's T5 (shared-memory per-tile depth) is the missing half. **The combined principle, contrasting the two sources**: a full win needs BOTH (a) ComputeRaster's candidate-set reduction via binning tiny tris to tiles (cheap, T1) AND (b) CudaRaster's per-tile-owned shared-memory depth election (removes the global atomic per fragment). ComputeRaster alone gives (a) but keeps the global atomic — which is why at our scale it would not beat us. **Adapt**: if we tile, do the depth election in `var<workgroup> atomic<u32>` (workgroup-scoped atomicMax on our packed 24b|8b word), flushing winners to the global id buffer at tile end — workgroup atomics are far cheaper than global. This is the synthesis of the two sources and the highest-ceiling lever. The no-64-bit constraint is unaffected: our 32-bit packed word works identically in workgroup address space.

## Dead-end confirmations (techniques present here that we have already refuted — do NOT resurface)
- **Conservative HiZ occlusion at tile/bin granularity** (`BinZ`/`TileZ` `InterlockedMin` + `if hiZ < zMin cull`, `TileRaster.hlsl:68-76, 174-194`; `RE_HI_Z` early reject `BinRaster.hlsl:40-43`, `PixelRaster.hlsl:74-77`): same conservative max-Z occlusion the mission refuted for holey foliage (a gap pins zmax to far plane → nothing tests as behind). ComputeRaster CONFIRMS the mechanism but it is no help for our workload. Additionally its HiZ is `globallycoherent` + `DeviceMemoryBarrier` (`TileRaster.hlsl:44-47, 184`) which is *expensive* — a trap at our scale.
- **Per-pixel mutex / contention-reduction depth (`USE_MUTEX 1` spin-lock, `PixelRaster.hlsl:122-138`)**: the "watertight" alternative to our relaxed atomic. It is a per-pixel spin-lock — far slower under 12-20× overdraw. CONFIRMS the mission's "reducing SW atomic-contention is not the lever / not the bottleneck" finding: the contention-eliminating path is the slow one.
- **Sub-pixel/area-based LOD-ish culling**: ComputeRaster has no LOD; its `CullPrimitive` is plain frustum cull (`TileRaster.hlsl:55-71`) and a between-tiles area check is absent. No new sub-pixel cull beyond what CudaRaster's "between-samples" already offers (see that brief's T1).

## Traps specific to this source (do not port blindly)
- `globallycoherent RWTexture2D<uint>` + `DeviceMemoryBarrier()` for HiZ reads (`TileRaster.hlsl:44-47, 184-185`): forces cross-workgroup coherence; very costly. WGSL has `storageBarrier()` but no per-resource `globallycoherent` qualifier — and we would not want it at 36M tris regardless.
- `[allow_uav_condition]` loops with explicit iteration caps "to avoid time-out" (`TileRaster.hlsl:170-171`): a sign the binning loop can run long; at our triangle counts these unbounded-fan-out loops are a hazard.
- The mutex color write (`USE_MUTEX`): correctness-over-speed, not for us.
