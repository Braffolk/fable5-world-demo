**Premise audit:** The premise is FALSE by direct whole-frame A/B measurement, off by ~6x. The idea asserts the resolve re-solves "~13ms+" of lighting per frame. The 90fps cost map (docs/perf-runs/2026-07-04-90fps-arc.md, whose own instrument note says whole-frame gpuWall A/B is the ONLY ground truth) measures: pure=1 (post removed) leaves lit-resolve+shadow-sample = 2.1ms eye / 1.6ms oblique (line 23); and bg-null + hide naniteResolve + hide naniteResolveVox = -0.5ms total (lines 37-39, "NOT the slab"). The idea reaches 13ms only by lumping in POST (5.5ms) — but POST is GTAO 3.7 (screen-space depth-neighborhood AO, already faded 90-240m), clouds (view-ray volumetric raymarch, there is no surface), screen-space bounce, contact shadows (screen-space depth march). None is surface-cacheable without replacing the algorithm; caching them "keyed by surface" is a category error (clouds have no surface; SSAO is defined on the screen depth buffer). One level up, the real dominant costs of walking 36.7ms (budget sketch line 74-79) are shadows-moving ~8ms and tri pixel-loop ~7.8ms. Both dominant slabs are rasterization the idea structurally cannot touch. MECHANISM assumption is also already realized in-tree and measured dead: NaniteGrass.ts kGuideLight (lines 620-695) bakes sunVis(PCSS x cloud x far) + probe irradiance PER GUIDE TEXEL each frame into a filterable rgba16f texture and the resolve takes ONE HW-bilinear tap (resolveLean) instead of the shadow-upsample + GI chain — this IS "shade into a surface cache, gather one tap." The idea's own foothold — the ProbeGI volume — is already a world-space cached irradiance for the diffuse-indirect term (NaniteResolve.ts:1371-1394), and the shadow sample is already half-res cached (S0). Every sub-term the idea names is either already cached one level up, or is rasterization/screen-space that a shading cache cannot address.

**Killer objections:**
- **The exact mechanism is already shipped and was measured to save ZERO ms (grass lean lighting)**
  - _severity_: fatal
  - _mechanism_: NaniteGrass.ts:620-695 (kGuideLight/resolveLean) bakes sunVis+probe-irradiance per surface texel each frame and the resolve gathers one filtered tap instead of the PCSS-upsample+GI chain — a literal per-surface radiance cache with a one-tap gather, on the single most shading-heavy tier (grass). Direct within-session A/B: p50 24.9 vs 25.0 (NaniteGrass.ts:134-141), identical even with full-res PCSS forced. It won nothing because resolve SHADING was never the cost; it is shipped OFF (?grasslean opt-in). Re-deriving the same cache for terrain/bark/leaf/voxel will reproduce the same null.
- **The idea cannot touch either of the two dominant slabs; it only attacks a ~2.1ms residual**
  - _severity_: fatal
  - _mechanism_: Walking 36.7ms is dominated by shadows-moving ~8ms (NaniteShadowClip depth-only strip re-raster, atomicMin Z, geometry — NaniteRaster.ts:151) and the tri pixel loop ~7.8ms (atomicMax visibility election, NaniteRaster.ts:376, runs BEFORE the resolve). A shading cache addresses neither: shadow maps are geometry rasterization, and you must run the visibility raster to know which surface a pixel sees before you can gather its cached radiance. The RASTER arc already closed the 7.8ms loop as 'intrinsic per-covered-pixel work, all structural levers dead' (task #67). Even a perfect zero-cost shade caches at most ~2.1ms of 36.7ms (~6%).
- **The deferred vis-buffer already shades each surface once per pixel — there is no shading overdraw to amortize**
  - _severity_: serious
  - _mechanism_: NaniteFrame.ts/NaniteResolve.ts headers: the resolve shades ONLY the winning fragment per pixel (deferred, no overdraw). The idea's 'reuse across the many pixels covering one surface patch' only pays if the cache is COARSER than a screen pixel — but a patch covering many pixels is a NEAR/large surface where per-pixel shading is already cheap and once-per-pixel. Caching coarser than a pixel there = under-shaded large near surfaces (banding/blockiness). The only reuse left is temporal for static surfaces, worth <=2.1ms and already the cheapest part of the frame.
- **No stable surface key exists; the DAG cut churns every moving frame, cold-invalidating the cache exactly when the frame is expensive**
  - _severity_: fatal
  - _mechanism_: There are no natural UVs (vis-buffer/cluster renderer). Option A (cluster+bary hash): NaniteCull BFS re-selects a DIFFERENT DAG cut against the stale HZB every moving frame (freeze=1 shows 'cut churn ~2.6', 90fps-arc.md:71; crownlod0 floods qRaster to 252k, user-issues-arc). A cluster-keyed cache is invalidated whenever the LOD cut reselects — i.e. across most of the field on every moving frame, precisely the frames that cost 36.7 vs 23.3 still. Option B (world hash-grid): sub-cm foliage detail needs an enormous grid or it blurs leaves; hash collisions bleed radiance between distinct surfaces. The diffuse part of option B already exists as ProbeGI (the idea's own 'foothold'), so only direct sun N·L (a dot product) remains — not worth a cache.
- **Staleness under moving clouds + per-frame wind smears in a forest, violating the absolute quality bar**
  - _severity_: serious
  - _mechanism_: cloudShadow is time-varying (NaniteResolve.ts:1326-1333) and wind is rebaked EVERY frame (NaniteGrass kGuideBake amp; voxel crowns now animate, user-issues-arc). The idea concedes 'moving-shadow/wind edges stay per-frame' — but in a forest nearly every foliage pixel IS a wind + moving-cloud-shadow edge, so the 'stays per-frame' exception swallows the win, and any budget-throttled stale texel shows lagged shadow/wind = smear. The quality bar forbids any visible regression (no blur/smear/pop).
- **A splat-from-cache adds a second election pass and does not reduce net work; atomics were never the bottleneck**
  - _severity_: serious
  - _mechanism_: If the gather is implemented as a scatter/splat (like NaniteVoxelRaster kVoxScatter), it hits the SAME atomicMax election as world1 and adds a second O(footprint) pass over cached elements on top of the tri raster. user-issues-arc:50 (verified): 'atomic-writes are NOT a bottleneck (ROP-pipelined since ~Fermi)... REAL perf lever = work-VOLUME.' NaniteVoxelRaster header: coarse splat is still O(footprint) per element. So splat-from-cache = more net work, not less. If implemented as a per-pixel gather instead, it is the grass-lean path = measured no-win.
- **A per-pixel gather at dpr2 is not free, and the resolve fragment is already at the 10-storage-buffer ceiling**
  - _severity_: serious
  - _mechanism_: DPR law (90fps-arc.md:26-30): frame ~= A + B·px, B~=3.2ms/Mpx eye; any new per-pixel pass touches 5.94Mpx. A gather needs surface-key derivation + fetch per pixel — comparable to the work the resolve already does. Worse, NaniteResolve.ts:369-382 + costmap HAZARD ('the limit really is 10; bind #11 = validation death, fast fake numbers') means a uint cluster/bary-hash cache buffer bound in the resolve fragment risks the 11th-binding silent pipeline kill. Grass-lean dodged this only by using a filterable TEXTURE for a smooth low-freq field; a per-cluster hash cache cannot be a smoothly-filtered texture.
- **It stacks a second temporal-reuse layer on TRAA, doubling ghosting/disocclusion risk in the exact regime that is already the live pain**
  - _severity_: minor
  - _mechanism_: TRAA already amortizes shaded color temporally at the screen level (the idea dismisses this as 'just TSR', but it is shipped and already reuses static shading). A surface cache is a SECOND temporal layer with its own disocclusion/staleness handling. The live pain (task #70, user-issues-arc #6) is MOTION VARIANCE + GPU thermal — a per-frame-budget cache with staleness-under-motion adds exactly the fragility that produces stutter/smear, for a term that is not the bottleneck.

## 2. Residual gaps that survive ALL THREE (the hole you suspect)

The three attack the 7.8/18.4ms raster loop and a ~0.5-2ms slice of resolve shading. Everything else in the 36.7ms walk is untouched:

1. **Shadow-map generation under motion — ~8ms. Largest single slab AND the measured stutter root.** Toroidal-clipmap strip re-raster of caster geometry (light-space, atomicMin-Z depth-only, NaniteShadowClip). No camera-space reproj, no surface-shading cache, no camera-cluster splat reaches *light-space*. `nanshadow=0` walking 28.8 vs 36.7; spike frames carry `nanite.shTotal +46-51k`.
2. **Screen-space POST — 5.5ms** (GTAO 3.7 + clouds/bounce/contact 2.3). View-ray / depth-neighborhood, half-res MRT, re-posed every moved frame. Not surface-cacheable at all (clouds have no surface; GTAO is defined on the screen depth buffer). Res-scaling ban removes the one measured lever.
3. **Grass per-pixel raymarch — 4.4ms.** Dense near field = max parallax + per-frame wind → the *worst* case for both reproj and cache; a view-dependent march into an animated field, so it must be re-raycast, never reused.
4. **Resolution-independent floor — A≈4.2ms** (submit / cull / HZB / shadow-cut traverse / vis-clear). Hard floor — and the three *add* full-screen passes on top of it (reproj scatter ~1.5ms + cache gather ~1ms, both at 3.3Mpx, un-scalable).
5. **GPU thermal DVFS slog** (fixed pose degrades after 150s). Bounded per-frame work does not reduce heat — part of the "stutter" is thermal, not work-variance.

Untouchable big-three sum (8 + 5.5 + 4.4) = **17.9ms — already above the 11-12.5ms p50 target before the new reproj/cache passes are added.** That is the hole.

## 3. Double-counting

**Yes — IDEAs 1 and 3 double-count the single 7.8/18.4ms raster pixel-loop.** Reproj makes the *coherent* frame's raster cheap; splat makes the *incoherent* frame's raster cheap — but there is one raster-loop cost, not two. On a coherent frame IDEA 1 already eliminated the re-raster (IDEA 3 has nothing to splat); on a disocclusion frame IDEA 1 falls back and IDEA 3 saves. Combined ≈ **max(the two), not sum** — presenting them as additive legs overstates the raster win ~2×.

Secondary inflation (same failure mode, not cross-idea): IDEA 2's "13ms" target folds POST (5.5ms, uncacheable) into resolve-shading (~2.1ms real) — a ~6× self-inflation of its own target.

## 4. Recommended next step

**Prototype a FOURTH axis first — light-space (shadow) temporal reuse / caster update-rate decoupling — not any of the three.**

- It is the only lever that hits the **8ms** slab (largest residual) *and* the measured stutter (freeze keeps spikes; `ablate=shadows` kills them). Every path to the mandate runs through it.
- **The temporal-reuse kernel of IDEA 1 is correct — it was aimed at the wrong buffer.** Light-space is far more temporally coherent than camera-space (the sun is ~static frame-to-frame; only the toroidal scroll from camera translation exposes new strips). The R1 exact-VP cache already proves static-shadow reuse works (static shadows 0.8ms); the 8ms is exactly the newly-exposed strips. Reuse is *valid* here where it was invalid for the camera vis-buffer.
- Concrete mechanism: decouple the toroidal-clipmap caster strip re-raster from frame rate — update coarse/far clip levels on an N-frame cadence or a texel-change budget and reuse light-space depth between updates; keep near levels per-frame. Orthogonal to resolution (no res-scaling implied).

Of the original three, **only IDEA 3 is worth a small spike, and only as a kVoxScatter *extension*** (not a parallel splat path — the ≤10 storage-buffer resolve ceiling forbids a second one), covering the sub-pixel population *not already voxel-splatted*: far trunks (already ~150-tri DAG roots) + the 20-60m leaf-mesh band. Expect **<0.7ms** (loderr=6 ceiling), and it needs a per-cluster aggregate attribute that risks the "far tree = one color" regression — a cleanup, not a mandate-mover. **Skip IDEA 1** (wrong axis + breaks TAA sub-pixel convergence) and **IDEA 2** (already shipped as grass-lean, measured 0.0ms).

Even with the 4th axis landed, the screen-space POST floor (5.5ms) stays a wall under the res-scaling ban and will need its own quality-preserving temporal-reuse angle (reproject GTAO/clouds with disocclusion guards) — effectively a fifth axis, covered by none of the three.
